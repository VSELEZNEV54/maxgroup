# Карта проекта и сопровождение Max Group

Рабочая среда разработки — локальный сайт Django. Правило для чатов и карта стека лежат в этом же репозитории. [AGENTS.md](../AGENTS.md) · [Архитектура](stack.md)

## Запуск и ежедневная работа

Запуск из корня проекта с работающим Docker

```sh
make up
```

Открывайте [сайт](http://localhost:8000/), [каталог](http://localhost:8000/catalog/) и [Wagtail](http://localhost:8000/admin/). При первом запуске команда создаёт файл `.env` с правами владельца, применяет миграции, собирает ресурсы, загружает страницы и лоты и создаёт локального администратора. Логин по умолчанию `manager`, пароль указан в локальном `LOCAL_ADMIN_PASSWORD`. В репозиторий входит только образец переменных. Для сброса локального пароля выполните `docker compose exec web python manage.py changepassword manager`. [Переменные окружения](../.env.example)

| Задача | Действие |
|---|---|
| Изменить текст, SEO или порядок разделов | В Wagtail откройте «Страницы» → «Макс Групп», выберите страницу, внесите правку, посмотрите предпросмотр и нажмите «Опубликовать». Заголовок страницы управляет H1, вкладка продвижения — поисковым заголовком и описанием. |
| Исправить подпись или фотографию в готовом макете | Раскройте соответствующий исходный раздел. В нём есть поля заголовка, первого абзаца, фото и кнопки. Список замен позволяет выбрать другую фразу раздела по её видимому тексту. |
| Добавить страницу | Создайте дочернюю «Страницу сайта» в нужном разделе. Добавляйте блоки текста, фотографий, видео или ссылок. |
| Изменить лот, общие контакты | Раздел «Автомобили» хранит карточки и редакторские поля. Ручная цена и обложка имеют приоритет при повторном импорте. Общие телефон, почта и ссылки находятся в «Настройки» → «Контакты и навигация». |
| Проверить заявку | Откройте «Заявки», затем «Доставка в CRM». На локальном сайте обе записи доставки имеют статус «Сохранена локально». По умолчанию внешняя отправка выключена. |
| Изменить код, CSS, существующий макет или файл данных | Прочитайте корневой `AGENTS.md`, измените исходник, выполните `make up` и откройте результат на порту 8000. Операция повторной синхронизации базы доступна через `docker compose exec web python manage.py sync_site`. |
| Проверить выпуск | `make test` проверяет Django, миграции и сценарии на отдельной тестовой БД. `make check-urls` обходит каждый адрес закрытого реестра выпуска, включая квизы и страницу 404. |
| Найти ошибку | `docker compose ps -a`, `make logs`, `docker compose logs --tail=100 setup`. У HTTP-ответа есть заголовок `X-Request-ID`; тот же ID находится в JSON-журнале процесса web. [Проверка приложения и БД](http://localhost:8000/health/) |
| Остановить и вернуться к работе | `make stop`, затем `make up`. База, фото и документы Wagtail хранятся в именованных томах Compose. |

Сборщик на Node.js 24 переносит согласованные макеты из `src/`, историю каталога и рекламные квизы в закрытый выпуск. В нём есть полные документы и реестр `source-manifest.json`. Команда `sync_site` связывает исходные пути с деревом Wagtail и лотами PostgreSQL. Для вложенных URL без собственной посадочной страницы используются служебные узлы. Публичный запрос проходит через Nginx и Gunicorn в Django. Цена, публикация, редакторское содержание, фильтры и форма берутся из действующего приложения. Файлы `dist*` генерируются автоматически. [Синхронизация](../backend/website/management/commands/sync_site.py)

## Загрузка машин и CRM

Для CSV с заголовком или JSON-массива обязательны `external_id`, `parent_path` и `name`. Путь модели уже должен существовать в каталоге. Дополнительные поля — `slug`, `year`, `price` в рублях, `price_label`, `partial`, `mileage`, `photos` и `available`. Для CSV используйте UTF-8 и разделяйте URL фотографий внутри поля знаком `|`. JSON принимает список ссылок. Одна строка JSON для проверки выглядит так.

```json
{"external_id":"supplier-123","parent_path":"/avto-iz-yaponii/toyota/prius/","name":"Toyota Prius 2023","year":2023,"price":2900000,"price_label":"под ключ во Владивостоке"}
```

```sh
docker compose cp cars.json web:/tmp/cars.json
docker compose exec web python manage.py import_cars supplier-one /tmp/cars.json
```

Выгрузка применяется одной транзакцией. Пара `источник + внешний ID` распознаёт обновление. Для снятия с продажи поставщик передаёт `available: false`; пропуск машины в частичной выгрузке сохраняет её состояние. Для автоматического импорта того же JSON задайте `CATALOG_FEED_URL` и `CATALOG_FEED_SOURCE`. После `make up` Celery Beat проверяет выгрузку каждые 15 минут, результат виден в «Импорты». [Импорт каталога](../backend/catalog/importer.py)

Для отдельного стенда доставки задайте `CRM_ENABLED=1` и выбранные назначения `CRM_DESTINATIONS`. amoCRM использует адрес аккаунта, действующий токен и числовые ID трёх полей сделки для UUID заявки, телефона и подробностей. Битрикс24 использует адрес входящего вебхука с доступом к лидам и текстовое поле `UF_CRM_…` под внешний UUID. Сначала проверьте поиск по UUID и создание записи в каждой тестовой воронке. [API сделок amoCRM](https://www.amocrm.ru/developers/content/crm_platform/leads-api) · [API лидов Битрикс24](https://apidocs.bitrix24.ru/api-reference/crm/leads/crm-lead-add.html)

Каждую минуту планировщик подбирает ожидающие доставки. У каждой CRM отдельное состояние. При неопределённом ответе воркер ищет уже созданную запись. Запись со статусом «Нужна сверка» возвращают в очередь командой `docker compose exec worker-crm python manage.py retry_delivery ID --confirmed-absent` после проверки внешней CRM. Старые локальные тестовые заявки сохраняют локальный статус при последующем включении интеграции.

## Статический предпросмотр макетов

Снимок CarHub для подборок хранится в `data/model-offers.json`. Команда `make refresh-offers` запрашивает опубликованный API поставщика, заменяет снимок после успешного получения всех моделей и пересобирает локальный выпуск. Дата и срок актуальности берутся из выгрузки. Для обычной разработки достаточно данных, включённых в выпуск. Для автономного сравнения макетов можно собрать и открыть статический предпросмотр. [Обновление предложений](../tools/refresh-model-offers.mjs) · [Фотографии моделей](../data/popular-model-photos.json)

```sh
node build.mjs --out=dist-support --strict
node serve.mjs 4319 dist-support
```

Адрес локального просмотра — `http://localhost:4319/`. Демо на GitHub Pages собирается с закрытой индексацией. Для приёмки поисковых настроек используется конфигурация основного домена.

## Инфраструктура рабочей версии

В рабочей среде планируется использовать тот же образ Django и отдельные процессы CRM и импорта. В локальном Compose работают PostgreSQL, отдельные Redis для кеша и очередей и один Celery Beat. Для пользовательских медиа по умолчанию подключён именованный том. Для S3 включите `MEDIA_BUCKET`, `MEDIA_CDN_DOMAIN` и передайте учётные данные через окружение хранилища. Контейнер Nginx раздаёт медиа уже импортированных макетов.

При первом развёртывании специалист дополняет этот раздел реальными сведениями. Пока хостинг, адреса стенда и рабочие аккаунты CRM не зафиксированы в этой документации.

| Что записать при запуске | Где поддерживать в актуальном виде |
|---|---|
| Домены, DNS, регион и идентификаторы ВМ, БД и хранилища. Владелец каждого аккаунта и способ запросить доступ | Реестр инфраструктуры в этом документе. Для паролей и токенов указывать ссылку на закрытое хранилище секретов. |
| Команды запуска на чистой машине, имена сервисов, переменные окружения, проверка готовности приложения | Рядом с Compose-файлом, файлом зависимостей и примером окружения. Пример содержит только названия и безопасные значения. |
| Адреса админки, панелей мониторинга, журналов и резервных копий. Получатель каждого оповещения и его замена | В этом документе, отдельно для стенда и рабочей среды. |
| Формы, идентификаторы воронок и полей, назначения заявок, способ авторизации, правила обновления токенов. Расписание источников каталога | Таблица интеграций в репозитории. Секретные значения хранятся в окружении или хранилище секретов. |

## Кто за что отвечает

**Редактор** пользуется правами Wagtail на дерево страниц и коллекции медиа. Группа «Менеджеры заявок» получает просмотр заявок и состояния их доставки. Группа «Сопровождение каталога» видит журнал импортов и карточки машин. Технический специалист выполняет повтор доставки через служебную команду. Создавайте отдельных пользователей и назначайте им нужную группу в панели Wagtail.

**Разработчик сопровождения** отвечает за код, миграции, ошибки интеграций и выпуск релизов. Профиль для найма — Python/Django, SQL/PostgreSQL, REST API, Linux и Docker. Для изменения публичных шаблонов нужны HTML/CSS, для редакторских блоков — знание Wagtail. Умение сопровождать Celery и разбираться с повторами интеграций проверяется на сценарии зависшей заявки.

## Что проверять при сбое

| Симптом | Порядок действий |
|---|---|
| Менеджер не видит заявку в CRM | Найти заявку в локальном журнале, открыть статус нужной CRM и внешний ID. При тайм-ауте сверить наличие записи в CRM по ID Max Group. При ошибке полей или авторизации исправить настройку, затем повторить только проблемную доставку. Продажам доступны контакты из локального журнала. |
| У лота старая цена или пропало фото | Найти источник, время последнего успешного импорта, число применённых и отклонённых записей. Проверить ручную поправку, опубликованную версию, вариант фото в хранилище и кеш карточки. После исправления повторить затронутую запись или партию по её ID. |
| Редактор видит новый заголовок, посетитель видит прежний | Сверить адрес, статус и время публикации, открыть публичную страницу анонимно. Проверить инвалидирование кеша страницы, а также связанной марки, модели или подборки. |
| Ошибка 5xx или замедление после релиза | В мониторинге определить время начала и затронутый маршрут. Найти запрос в журналах Nginx и Django по ID, сопоставить с версией образа, задержками PostgreSQL и загрузкой воркеров. При необходимости развернуть предыдущий образ, совместимый с текущей схемой БД. |

Локальные JSON-журналы доступны через `make logs`. Для рабочего сервера предусмотрены Cloud Logging и Cloud Monitoring. Нужные показатели — доступность, время ответа, 5xx, возраст старейшей ожидающей доставки, время последнего успешного импорта и резервной копии. Порог оповещения привязывают к допустимой задержке заявки или обновления цены.

## Релизы, резервирование и передача

Для локального архива базы и загруженных медиа выполните команды из корня проекта. Папка с копиями исключена из Git.

```sh
umask 077
mkdir -p .local.nosync/backups
backup_stamp=$(date +%Y%m%d-%H%M%S)
docker compose exec -T db pg_dump -U maxgroup -Fc maxgroup > ".local.nosync/backups/db-$backup_stamp.dump"
docker compose exec -T web tar -C /srv/media -cf - . > ".local.nosync/backups/media-$backup_stamp.tar"
```

Для проверки создайте отдельную пустую базу через `createdb` и восстановите в неё дамп через `pg_restore --exit-on-error`. Сверьте число страниц и автомобилей, затем проверьте фото с копией тома загрузок. При подготовке проекта локальный дамп успешно восстановился в отдельную проверочную базу с 695 лотами.

- Путь релиза — тесты, сборка образа, стенд, проверка редактирования страниц и тестовой заявки, выпуск той же версии в рабочую среду. На стенде формы направляются в тестовые воронки. При изменении схемы заранее описывается совместимость предыдущего образа с миграцией и способ восстановления.
- Для управляемого PostgreSQL включаем автоматические копии и восстановление на момент времени. Для медиа — версионирование и отдельную резервную копию оригиналов. Проверку выполняем восстановлением в отдельный стенд и сверкой страниц, фото и связей заявок с CRM. В журнале эксплуатации указываем дату успешной проверки и фактическое время восстановления. [Резервные копии PostgreSQL](https://yandex.cloud/ru/docs/managed-postgresql/concepts/backup)
- При передаче сайта новый специалист самостоятельно поднимает стенд по инструкции, изменяет заголовок и обложку, повторно импортирует один лот, находит тестовую заявку в обеих настроенных воронках и диагностирует сбой одной доставки. Обновления схемы, команд развёртывания, структуры URL и полей CRM документируются вместе с соответствующим изменением в коде.
